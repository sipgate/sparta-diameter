# Identifier Types — Design

See ADR-0005 for the decision rationale and rejected alternatives.

## Records

```java
record HopByHopId(int value) {}
record EndToEndId(int value) {}
```

## Type hierarchy

`IncomingCommand` is an interface with accessor methods, not a bare marker:

```java
interface IncomingCommand {
    HopByHopId hopByHopId();
    EndToEndId endToEndId();
}
```

`IncomingRequest`, `IncomingAnswer`, `OutgoingRequest`, and `OutgoingAnswer` are abstract classes (not interfaces). They encode identifier ownership in the type system:

- `IncomingRequest<T, A>` — extends `Request<T, A>`, implements `IncomingCommand`; stores `final HopByHopId` and `final EndToEndId`, provides the `hopByHopId()` / `endToEndId()` implementations.
- `IncomingAnswer<T>` — extends `Answer<T>`, implements `IncomingCommand`; delegates identifier storage to `Answer`.
- `OutgoingRequest<T, A>` — extends `Request<T, A>`; carries no identifiers; exposes `writeTo(DataOutputStream, HopByHopId, EndToEndId)`.
- `OutgoingAnswer<T>` — extends `Answer<T>`; holds final identifiers (inherited from `Answer`); exposes `writeTo(DataOutputStream)`.

## Command class structure

Each command type is a **interface** that carries AVP mixin bounds and an F-bounded type parameter `T`. The `In` and `Out` concrete classes are nested `final` classes inside that interface:

```java
// enclosing interface — AVP mixins + generic signature only
public interface CapabilitiesExchangeRequest<T extends CapabilitiesExchangeRequest<T>>
        extends HasVendorIdAVP<T>, /* ... */ {

    // In — wire-parsed; setters throw UnsupportedOperationException
    @DiameterRequest(CMD_CAPABILITIES_EXCHANGE)
    final class In extends IncomingRequest<In, CapabilitiesExchangeAnswer.Out>
            implements CapabilitiesExchangeRequest<In> {
        private In(HopByHopId hopByHop, EndToEndId endToEnd, boolean retransmitted) { ... }
    }

    // Out — application-created; identifiers injected by Session at send time
    final class Out extends OutgoingRequest<Out, CapabilitiesExchangeAnswer.In>
            implements CapabilitiesExchangeRequest<Out> {
        public Out() { ... }
    }
}
```

Answer types follow the same pattern with `IncomingAnswer` / `OutgoingAnswer`.

## Annotation placement

`@DiameterRequest` is placed on the `In` nested class inside the request interface.
`@DiameterResponse` is placed on the `In` nested class inside the answer interface.

`Command.initializeCommandTypes()` scans for these annotations via reflection. For `createAnswer()`, the `Out` answer class is found by convention: given the registered `XxxAnswer$In` class, walk up to its enclosing class (`XxxAnswer`) and find the nested class that extends `OutgoingAnswer`.

## Identifier ownership

| Object | Identifiers | Set by |
|---|---|---|
| `IncomingRequest.In` | `final HopByHopId`, `final EndToEndId` | Wire parser via `DiameterMessageFactory.createForParsing` |
| `IncomingAnswer.In` | `final HopByHopId`, `final EndToEndId` | Wire parser via `DiameterMessageFactory.createForParsing` |
| `OutgoingAnswer.Out` | `final HopByHopId`, `final EndToEndId` | `DiameterMessageFactory.createAnswer()`, copied from `IncomingRequest` |
| `OutgoingRequest.Out` | none | `Session.send()` generates them, passes to `OutgoingRequestEncoder` via `OutgoingRequestEnvelope` |

## DiameterMessageFactory

Two public factory entry points:

```java
// Public — called by the decoder and by tests to simulate inbound messages.
// Uses raw Class because the parser cannot know the concrete type at compile time.
public static IncomingCommand createForParsing(
        Class type,
        HopByHopId hopByHop,
        EndToEndId endToEnd,
        boolean retransmitted);

// Public — creates an outgoing answer from an incoming request.
// Copies hop-by-hop and end-to-end identifiers, sets Result-Code,
// and populates Destination-Host / Destination-Realm from the request origin.
public static <A extends OutgoingAnswer<A>> A createAnswer(
        IncomingRequest<?, ?> request,
        long resultCode);
```

`Out` request classes have public no-arg constructors and are instantiated directly by application code — no factory method is needed.

## OutgoingRequestEnvelope

A record that bundles an `OutgoingRequest` with the identifiers generated by `Session.send()` for delivery to the encoder pipeline:

```java
record OutgoingRequestEnvelope(OutgoingRequest<?, ?> request, HopByHopId hopByHop, EndToEndId endToEnd) {}
```

## Pending-requests map

```java
ConcurrentHashMap<HopByHopId, CompletableFuture<?>> pendingRequests;
```

The key is `HopByHopId`, not a raw `int`.

## Encoders

Both encoders are Netty `MessageToByteEncoder` subclasses:

```java
// OutgoingAnswer already holds HopByHopId and EndToEndId as final fields
class OutgoingAnswerEncoder extends MessageToByteEncoder<OutgoingAnswer> {
    void encode(ChannelHandlerContext ctx, OutgoingAnswer answer, ByteBuf out);
    // delegates to: answer.writeTo(new DataOutputStream(new ByteBufOutputStream(out)))
}

// Identifiers are injected at send time via the envelope
class OutgoingRequestEncoder extends MessageToByteEncoder<OutgoingRequestEnvelope> {
    void encode(ChannelHandlerContext ctx, OutgoingRequestEnvelope envelope, ByteBuf out);
    // delegates to: envelope.request().writeTo(out, envelope.hopByHop(), envelope.endToEnd())
}
```

`IncomingRequest` and `IncomingAnswer` have no `writeTo` — wire-parsed objects are never re-serialized by the session layer.

## GenericCommand

`GenericCommand` follows the same `In` / `Out` split, but does not extend `OutgoingRequest` or `OutgoingAnswer`. Both identifiers are **required** in the `Out` constructor (relay use case always has them):

```java
public static final class Out extends GenericCommand<Out> {
    public Out(int commandCode, boolean request, boolean proxiable,
               boolean error, boolean retransmitted, int applicationId,
               HopByHopId hopByHop, EndToEndId endToEnd) { ... }

    public void writeTo(DataOutputStream out) throws IOException {
        writeTo(out, storedHopByHop, storedEndToEnd);
    }
}
```

`GenericCommand.Out` is written directly — it is not sent via the standard `Session.send()` path.

## ErrorAnswer

`ErrorAnswer` is application-created, extends `OutgoingAnswer`, and sets the E-bit. Instantiated via a static factory:

```java
public static ErrorAnswer create(int commandCode, boolean proxiable,
                                 int applicationId,
                                 HopByHopId hopByHop, EndToEndId endToEnd);
```

## Runtime guard on `In` setters

`Command.setAVP` checks `this instanceof IncomingCommand` and throws `UnsupportedOperationException` if true. Matches the Java unmodifiable-collections contract.
